# Chicago 311 点瓦片渲染试点

2026-11-17 在独立 Docker 项目 `geocsv-deck-pilot` 验收，入口为 `http://127.0.0.1:18089/`。在「Chicago 311 · deck.gl 试点」选中 `Chicago-311-2024-01.geojson` 后，地图工具栏可以在「原生 MVT」和「deck.gl 试点」之间切换。相机保留当前中心、缩放和朝向。切换到字段着色、透视联动或网格视图时，地图使用原生路径。试点加载失败时会提示并恢复原生路径。

数据是阶段 02 保存的公开样本，含 2024 年 1 月 **89,807** 条芝加哥 311 点。验收实例重新导入同一份 GeoJSON，SHA-256 为 `0f70242216cd5d9720def183c82534fa0ae4215eb6af452f3dfbe203865b1095`。社区边界单独导入，仅用于验证多图层顺序。[样本筛选与来源](02-chicago-311.md#数据范围) · [芝加哥市数据目录](https://data.cityofchicago.org/d/v6vf-nfxy)

## 数据如何到地图

- [PostGIS 瓦片接口](../../server/src/controllers/tileController.ts)根据 `z/x/y` 求瓦片边界，以空间索引筛选当前文件的记录，再将几何切成 `default_layer`。数据库要素 ID 写入 MVT 要素标识，两个渲染器请求同一地址和版本。
- [地图工作台](../../client/src/features/map/components/MapView.tsx)继续用 MapLibre 管理相机、底图和业务图层顺序。试点关闭该文件的原生绘制层，在对应顺序用 [deck.gl 适配器](../../client/src/features/map/deckPointLayer.ts)接管普通点绘制。适配器及自托管 MVT 解码 Worker 在选用试点时加载。
- 原生拾取与 deck.gl 拾取均将文件 ID 和瓦片要素 ID 交给 [App 的地图点击处理](../../client/src/App.tsx)。当前页缺少该要素时，请求带 `featureId` 的场景分页接口；属性表选中后，地图仍用查询得到的原始几何定位和高亮。

本次固定 deck.gl 9.4.1、MapLibre GL JS 5.17.0 和 loaders.gl MVT 4.5.4。使用 `MapLibreOverlay` 的交错模式，共用 WebGL2 上下文，`MVTLayer` 采用二进制瓦片解码。[MapLibre 集成](https://deck.gl/docs/developer-guide/base-maps/using-with-maplibre) · [MVTLayer 接口](https://deck.gl/docs/api-reference/geo-layers/mvt-layer) · [9.4.1 版本](https://github.com/visgl/deck.gl/releases/tag/v9.4.1)

## 对照方法

- Windows 主机，Ryzen 7 6800H、16 GB 内存，Chrome 157.0.8103.79，浏览器实测 WebGL 渲染器为 RTX 3060 Laptop GPU，通过 ANGLE / Direct3D 11。浏览器窗口 1440 × 960 CSS 像素，地图 **823 × 520**，DPR 1，使用空白底图以避免外部请求影响。
- 首屏中心 `[-87.715367, 41.834074]`、缩放 `9.19847`。从选中图层计时，直到当前视口瓦片就绪且浏览器再过两个绘制帧。每轮新建浏览器上下文，两条路径轮换顺序，PostGIS 使用同一已启动实例。
- 用 900 ms 将相机移至 `[-87.637, 41.878]`、缩放 `12.25`，再返回起点。记录第一次前往，以及同一页面返回后再次前往时的 `requestAnimationFrame` 帧间隔。帧间隔包含浏览器和渲染器开销。
- PostGIS 按视口范围统计点记录。网络只统计成功返回的业务 MVT，按瓦片地址去重，字节数取实际响应的 `Content-Length`。解码后按 MVT 要素 ID 去重，可以区分跨缩放重复加载与实际覆盖的数据规模。

首次打开的四张瓦片地址一致。往返的累计记录包含同一要素在不同缩放级别的编码，按要素 ID 去重后两者均为 89,807。重走轨迹仍观测到原生路径返回 2–3 次瓦片响应、试点返回 1–5 次。试点额外按需加载约 966 kB 的 JavaScript 和 98 kB 的解码 Worker，这两项是构建产物大小，未计入 MVT 表格。

这组数据比较的是**普通点渲染**。按本机结果，日常点图层继续用原生 MVT。后续需要 GPU 热力、网格聚合或轨迹时，可以用现有适配入口针对具体任务做单独对照，明确聚合的数据范围与精度。本轮比较范围为芝加哥约 9 万点与一台测试设备。

## 交互回归

- 在同一视角切换两种渲染器，浏览器记录的相机和视口一致。原生 MVT 点击要素 `89754` 后定位到 4,488 页。deck.gl 点击要素 `89659` 后定位到 4,483 页，并在属性表选中同一行。点击该行后，地图回到 PostGIS 返回的原始坐标。
- 加入 77 个社区面后，使用图层排序控制把点层放到面层下方，deck.gl 绘制顺序随之更新。关闭点层及切回原生时移除试点绘制层，反复切换后地图中只有一个活动的 deck.gl 层组。阻断试点代码加载时，界面提示并恢复原生 MVT。
- Docker 生产构建和 12 项底图回归测试通过。独立试点和原有 `localhost:8088` 的健康检查均返回 200。
