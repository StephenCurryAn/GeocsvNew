# Docker 实例验收 · 芝加哥 311 服务请求

2026-11-16 在独立 Compose 项目 `geocsv-public-case` 验收。四个容器均健康，Web 入口为 `http://127.0.0.1:8084/`。镜像与 02 四面样例已验收的镜像一致。主应用和数据库各自使用原来的项目与数据卷。

## 数据范围

- [芝加哥市 311 Service Requests](https://data.cityofchicago.org/d/v6vf-nfxy) 是约千万级的动态数据源。本次用其 `/resource/v6vf-nfxy.json` 接口，按 `:id` 升序分页取出 2024 年 1 月全部符合条件的记录。时间条件为 `created_date >= '2024-01-01T00:00:00.000' AND created_date < '2024-02-01T00:00:00.000'`，要求经纬度非空，并排除 `upper(sr_type) = '311 INFORMATION ONLY CALL'`。保留坐标、请求类别、所属部门、状态、上报来源、日期、小时、星期及来源记录的社区编号。没有请求住址字段。
- 通过 [芝加哥市社区边界](https://data.cityofchicago.org/d/igwz-8jzy) 的 `/resource/igwz-8jzy.geojson` 取得 77 个社区。保留官方社区名称、编号与原始面几何，两层数据均按 EPSG:4326 上传。
- 下载与导入均为 **89,807 条点记录、77 个面**。点数据包含 99 种请求类别和 24 种上报来源。两个原始下载产物和逐次分析结果在本机保存，数据和测试库未加入 Git。

## 从上传到归档

1. 通过场景接口上传面和点，在同一场景中使用 `spatial_pivot@1` 分别按请求类别与上报来源做面内计数。两次各得到 77 行，分别为 99 列与 24 列分类值，排除边界的匹配数均为 **89,661 对**。这是点与面的匹配次数。
2. 按唯一社区名称把计数结果关联回原始边界，得到 `total_requests` 与 `pothole_requests` 两个数值字段。将这份 77 面的派生 GeoJSON 上传到同一场景，保证 Moran/LISA 使用原始边界精度。
3. 用 `spatial_autocorrelation@2` 分别执行下表三次运行。算子版本为 `moran-lisa/2.0.0`，置换次数 199、种子 42。基于总量的两个任务使用同一输入摘要，三次运行均得到完整的 77 行局部结果。
4. 两种算子均通过 Nginx 提交计划，重复使用同一请求键取回同一个 Run，再用任务历史读取 Artifact、分页、GeoJSON 和 CSV。单次记录的大文件上传约 13 秒，五次分析各约 2.2–2.8 秒，这些是本机单次联调耗时。

## 额外模型验证 · DBSCAN

在同一个 Docker 数据库用 SQL 试跑 PostGIS `ST_ClusterDBSCAN`。输入为 6,525 条坑洞投诉点，转换到 EPSG:26916，参数为 150 米、最少 15 点，按稳定要素 ID 排序。返回 17 个簇，487 点入簇，6,038 点标记为噪声。簇数随参数变化。这次在数据库中验证了点聚类可用性，模型目录、任务协议及前端表单尚未接入该算子。[PostGIS 函数说明](https://postgis.net/docs/ST_ClusterDBSCAN.html)
